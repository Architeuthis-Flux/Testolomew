# Testolomew

Test bed for Jumperless V6 ideas on a wuxx nanoCH32H417 (CH32H417QEU6). The design context for V6 lives in `~/Desktop/V6pile` (start with its `CLAUDE.md`); the firmware this is meant to feed is `~/Documents/GitHub/JumperlOS`.

## Commands

- `pio run` builds; `pio run -t upload` flashes with wlink through the onboard WCH-LinkE (OpenOCD's upload crashes on reset with this chip, so `upload_protocol = wlink`); console is the WCH-LinkE serial port at 115200.
- `pio test -e native` runs the host-side tests (pure code only: the fit, the tracker, the row grid, the LED renderer, the paint brush, the button classifier, the menu, the UI shell and the camera; the list is `build_src_filter` in `platformio.ini`).
- `cd tools/hostsim && make check` runs the whole firmware on the host against `scenes/check.txt` (the verbs, a simulated probe, the dumps, Home and the Settings menu driven from the console, the held-control leak, a Result panel, a reset that leaves the modes alone, the settings written after they settle); `make screens` renders every screen to `tools/hostsim/out/` and the montage to `docs/screens-simulated.png`. `tools/hostsim/README.md` has the script directives.
- The console's `:verbs` (`:help` lists them) are the way to see and drive the screen without a hand on the board: `:screen` (the app, the panes, the menu page with its items, the probe, the play state, the camera), `:screen:ascii`, `:leds`, `:log`, `:stats`, `:ui open|menu|root|close|back|enter|hold|up|down|left|right|go <label>`, `:key <control> [tap|down|up|hold|xN]`, `:joy <x> <y>`, `:probe row <r> <h>` / `:probe x y z` / `:probe off`, `:load` (what draws from the 3.3 V rail and changes - the strip's frame current window, the display, the sensors, the heartbeat - with `:load strip|display|heartbeat|sampler on|off`, `:load sensors on|off|lp|ln|<n>` and `:load lcd <MHz>` to take each away for a power bisect; 2026-09-20: `sensors off` stopped the backlight's flicker). `python3 tools/screendump.py <port> out.png` grabs the screen as a PNG (`--ascii` for text). Type them on the monitor, or `python3 tools/readport.py <port> 3 out.txt $':screen\r'` (the `$'...'` quoting so the shell sends a real carriage return).
- Editing `platformio.ini` changes the project checksum and the next PlatformIO run - the IDE extension's background one included - empties `.pio/build`, which has killed a flash in progress. Build, copy the ELF out, and flash the copy with `~/.platformio/packages/tool-wlink/wlink flash <elf>`. If `wlink flash` connects and erases but never finishes the first write, the WCH-LinkE has wedged: a USB device reset (pyusb + libusb, vendor 0x1a86 product 0x8010) fixes it without unplugging. `Error while fastprogram: [41, 01, 01, 05]` is the V3F fetching the flash being written (no instruction cache; the program never completes - the core's `ch32h4_park.c`): ALWAYS park it before a flash. `pio run -t upload` does (`scripts/park_before_upload.py` sends the console command `F`); flashing by hand, send `F` on the serial port first, then `wlink flash <elf>`. After that error the WCH-LinkE drops off USB for 20-40 s and returns by itself; wait for `/dev/cu.usbmodem<serial>` and flash again. If wlink answers `protocol error 0x55` to everything (status, erase, reset), it is wlink's chip AUTO-DETECTION failing on a chip that is halted or erased, not a dead chip: `wlink status --chip CH32H41X` attaches at once (found 2026-09-21; on 2026-09-19 the same state was taken for a bricked board and waited out for hours). `upload_command` in `platformio.ini` now names the chip, so `pio run -t upload` never depends on the detection; by hand, always `wlink flash --chip CH32H41X <elf>`.
- The console is captured with `tools/readport.py <port> <seconds> <outfile> [keys]` (one program at a time may hold the port). `X` (or `:stats`) is the service table (per-service run time - the first thing to look at when anything stutters), `e` steps through the apps and prints each app's draw time, `n` prints the LED strip's frame statistics, `m` the sensor bus's resets and failed reads.
- `pio run -t compiledb` regenerates `compile_commands.json` for clangd.

## Rules of the house

- Match JumperlOS: Arduino framework, feature folders under `src/` with bare `#include "Foo.h"` (every folder is on the include path via `scripts/src_subdirs_include.py`), modules are `Service` subclasses registered with `jOS` in `main.cpp`, `.clang-format` is JumperlOS's (4 spaces, spaces inside parentheses, no column limit), SPDX header on every file.
- Keep the C++ plain: structs, free functions for drivers, one singleton class per service. No templates, exceptions, STL containers or inheritance beyond `Service` - with one deliberate exception, `src/ui/UiStream.h`, a `Stream` so the console can print through it to the serial port and the log screen at once (JumperlOS's Jerial is the same thing).
- `src/jos/JumperlOS.h` mirrors the `Service`/`jOSmanager` interface of JumperlOS's `src/JumperlOS.h`. Do not add scheduler features here that JumperlOS lacks; the point is that modules port over unchanged.
- Every pin comes from `src/board/BoardPins.h`. Modules register their own console commands with `consoleAddCommand()`; `Console.cpp` knows no module.
- Pure math that can run on the host goes in its own `.cpp` with no Arduino includes and gets a test under `test/`.
- Values that are guesses are marked `ASSUMPTION` in the source (sensor pitch, the PA14 power pin, the probe tip offset). Replace them with measurements; do not build on them.
- The breadboard LEDs come before the display: the LED service runs at HIGH priority every 20 ms with its own DMA channel, and the Display service will not start a draw that would make it late. Nothing in the loop may hold it for tens of milliseconds - draw through `src/display/FastDraw.h`, not GFX's text/line/rect (60x slower on this chip), and keep the sensor read's waits short (`TMAG5273.cpp` talks to the I²C block directly for that reason). Dumps over the console go a row a tick through `DumpService`, never in one print.
- The screen is an app from the table in `src/apps/Apps.cpp` (`UiApp`: enter/exit/tick/draw/event/generation, JumperlOS's `apps[]` shape) with the shell (`src/ui/UiShell.cpp`) as the one owner of the controls: an app gets its own controls and never A or B; Home (opens on Settings, the centre cell), the Settings menu (opens where it was last used; B held closes everything and keeps the page; a select HELD on a value tweaks it over the app with the value along the bottom), a Confirm and a Result panel take the buttons and the joystick; a control still down when a pane closes is swallowed until released. `src/ui/` knows no module (the grep `MagView|magLocator|probeLeds|Play.h|RowCounter|MagArray` over `src/ui/*` bar `Camera.*` stays empty); a new app is a file in `src/apps/`, a row in the table and an icon in `Icons.h`. The Settings menu (`src/apps/SettingsMenu.cpp`) binds a value with side effects through a get/set pair, never a mirror variable.
- `docs/knobs.md` is the reference card for every setting and compile-time knob (start there in a new chat), with the controls and the apps in its section 2; `docs/wireless-probe-sensing.md` has the reasons.
- The array never zeroes blind at boot: the saved zero is put back (when none is saved - first boot, settings wiped by a chip erase - the compiled-in `MAG_ZERO_AT_BOOT` is), then checked against the first 64 frames of readings: their difference from the saved zero is adopted as the zero when no dipole explains it (drift since the zero was saved: Kevin's bench read 0.05 mT with the probe away, 2026-09-24), and kept when one does, because the probe may be lying near the board and a zero taken then eats its field (2026-09-19: 0.15 mT off, misfit 20-50 %, the height 5 mm out). `z` zeroes afresh - only with the probe well away - and `Y` takes a known magnet back out of a fresh zero. When `z` is taken cleanly, its `zero=` lines from `s` are what to paste into `MAG_ZERO_AT_BOOT`. The sensor round-robin runs on the V3F (`src/magarray/MagSampler`), which reads the I2C block's registers directly; anything else that needs the bus pauses it (`pauseSampler`/`resumeSampler`). The V3F has no sub-millisecond clock: its `micros()` is noise, use `millis()` there. It has no instruction cache either: a loop it runs goes in ITCM (`__itcm_func`), from flash it ran at a third of the pace. On the V5F, too, a `static const` table read per pixel/LED is a flash DATA read the I-cache does not help with (the WS2812 symbol table cost 2.6 ms a frame): compute small tables or put them in RAM.
- Menu items the settings module does not save (`unsaved[]` in `src/settings/Settings.cpp`: row mode, chain on, V5 stream, play mode) are modes; the settings module captures every item's default from its getter after the modules have begun (it registers last), so a load or a reset never forces a mode. The sim's boot line checks it.
- Console output goes out by DMA (`src/console/SerialDma`): print freely, but never `Serial.print` beside it after `uiStream.begin()` (it interleaves), and the ring is 4 KB - a print bigger than that waits.
- The smoothing levers were set by `tools/hostsim/pencil.cpp` (lag versus jitter); change them there first. Since 2026-09-27 every compile-time default is the bench's setting as Kevin had it (knobs.md section 4's table); the host tests pin the reference look and levers in their setUp, and the scenes start with `@reference`. `SETTINGS_TUNING_VERSION` in `Settings.h` is bumped when the tracker/smoothing defaults improve, so saved older values yield to the new defaults.
- Build in a private directory when the IDE is open: `PLATFORMIO_BUILD_DIR=<somewhere outside the project> pio run` - the IDE's PlatformIO wipes `.pio/build` mid-link otherwise.
- The LED chain's current is budgeted per frame in `ProbeLedService::sendFrame` (every LED dimmed by the same factor when a frame would draw more): the menu's "budget mA" and, below it, the compile-time ceiling `PROBELED_STRIP_HARD_MAX_MA` (2 A) that nothing can raise. Anything new that lights LEDs goes through `stripRgb[]`/`sendFrame`, never `ledStripSet` directly; the current model (`PROBELED_MA_PER_CHANNEL`) is an assumption for the V5's 1010 LEDs, kept cautious. The V5 browned out under a painted board at 600 mA budgeted by an 8 mA model (2026-09-19).
- Anything the menu can edit is saved to flash by `src/settings` with no further work: add a menu item and it persists (keyed by page and label - renaming one resets it to its default; a mode that must not persist goes in the `unsaved` list in `Settings.cpp`, as row mode and the V5 stream do). A commit holds the loop ~70 ms (measured as a 79 ms gap in the LED frames), once per settled change - and never while the menu or a tweak is open (2026-09-28: the hitch read as "the setting applying later"; it waits up to 30 s, or for the panes to close). The console's command table (`CONSOLE_MAX_COMMANDS`) and the menu's item table (`MENU_MAX_ITEMS`) both fill silently but for a boot-time line; a command that "does not exist" was probably the 33rd.
- The breadboard's 5 V rail is small: a V5 browned out under a wide LED glow at full brightness. Every strip frame goes through the current budget in `ProbeLedService::sendFrame` (menu "max mA"); a far probe's wide bell at the peak is exactly what the budget is for (2026-09-27: the dim far glow of its own went at Kevin's request - one colours/height mapping for every state). Do not add an LED effect that bypasses it.
- A reboot's cause is on the console before the banner: the core prints `rst=... por` (the rail went down: every brown-out capture so far), `soft` alone (a flash, the debugger), `iwdg`/`lockup` (a firmware fault). Right after the banner the flight recorder (`main.cpp`, `.xcore` RAM that a reset does not touch) says what the board was doing when it reset: the chain's mA and biggest step, whether a settings write was in progress or the chain had just been re-lit, the fit's state, the screen's pane and menu item. Read those two lines before blaming anything.
- A saved zero is in the sensor's own frame (`sensorzero=`); changing a sensor's row (magcal) no longer needs a fresh `z` (2026-09-21: it did, and the MMC's stale board-frame zero read as a 0.09 mT phantom that the far mode took for a probe). What writes a zero to flash: `z`, the zero audit (`:audit`, docs/knobs.md section 6), `Y` and the settling of a provisional zero (all through `MagArray::shiftBaseline`); the offset filter that follows the drift (Phase 3, `MagLocator::keepZeros`) moves the live baseline only, never the saved zero.md` section 6) write a zero to flash: one sensor cannot tell its zero error from a far probe, the other eight can when the probe is near.
- Flash the safe way: `:load strip off` (see "cleared"), `F` (see "parked" - no reply, no flash), `wlink flash --chip CH32H41X --speed low`, "Testolomew" on the console within ten seconds. The Arduino core is patched at every build by `scripts/patch_core.py` (a weak `ch32h4_v3f_before_wake()` before the V5F's wake, where the sketch darkens the LED chain); if that script complains, the core moved and the patch needs a look before anything is flashed.
- The LED ceiling is 800 mA by the 12 mA model (`ProbeLedService.h`; the default budget is 800 too since 2026-09-27, the bench's setting - 600 until then); 900-1100 is what browned the board out. Do not raise the ceiling without a supply of the LEDs' own.

## Hardware facts that bite

- Only PA5–PA7 and PE2–PE6 are fixed 3.3 V pins. Everything else is on the VIO18 rail, which resets to 1.2 V; the Arduino core sets it to 3.3 V at boot (`boardVioIs3V3()` checks). Any other framework must set `PWR->CTLR[12:10] = 3` first.
- I²C has no internal pull-ups on this chip. SCL/SDA pairs are fixed by the silicon (PA8 goes with PC9).
- The array mixes sensor types (`MagArrayConfig.h`'s table: type, bus, address, pins, place, rotation, gain, face, calibrated per slot): eight TMAG5273s and, since 2026-09-21, one MMC5633NJL at the centre on the back, on its own bus (PF12/PF13), its row measured with `tools/magcal` - FAR ONLY by default since 2026-09-28 (`MAG_MMC_MODE_AT_BOOT` far, the menu's `tools / MMC` off / far / on, `:mmc on|far|off`: in far mode it is ramped into the fit only as the TMAGs' error bar opens up and left out near the board, where Kevin found "the readings have been 100x sketchier since we added that one"; switched out entirely from 2026-09-22 to then). The fit weights each sensor per frame by its noise plus 6 % of its reading (`magSensorFrameWeight`: a TMAG is 1, the MMC 37 far and 1 close in), holds the magnet's strength - LEARNED from the near fixes since 2026-09-22 (`MagLocator::measureStrength`, `MAGLOC_STRENGTH_*`, kept in the settings as `strength=`; `MAGLOC_MAGNET_STRENGTH` 4232 is only where a fresh board starts: held at the wrong strength a weaker magnet fits too high and off along the board and no calibration tap takes) and held because far out the MMC alone cannot tell a weak magnet near from the real one far and leans the direction on the last good fix (`MAGLOC_AXIS_PRIOR_MT`); the presence levels scale per type. `docs/knobs.md` has the numbers and the bench state; the far mode is verified in the simulator, not yet on the bench (a clean `z` with the probe away first).
- TMAG5273 I²C addresses are volatile: reassign after every power-up, one sensor powered at a time. Its sign convention is positive for field going *into* the package top (see `MagArray::toBoardFrame`). Its 1-byte-read-mode CRC does not work (TI errata by forum post; see `docs/magnetometer-fusion-prior-art.md` §2.3), so corrupted reads are caught downstream (median filter, the tracker's gate), not on the bus.
- The LED strip's data line (PD7) couples into the sensor I²C wiring on the bench: the I²C block takes the glitch for a STOP and drops out of master mode mid-read. The read code copes (a glitched read fails in microseconds and is retried), but keep that wire away from SCL/SDA, and do not route SPI clocks to header pins for nothing (LedStrip switches its SCK pad back to an input).
- GFX drawing is slow here (drawPixel 0.5-2.5 µs, a line 3 µs a pixel, a size-2 character 200 µs) while a plain buffer write is 40 ns: MagView's boot benchmark line prints the numbers. The scene, menu and log draw through `FastDraw.h`.
- The platform is pinned to a commit in `platformio.ini`; the CH32H4 Arduino core is days old, so bump deliberately.
- The LCD backlight flickers with the dipole fit (2026-09-20, bisected with `:load`: sensors, sampler, strip, display and heartbeat are not it; `:load fit off` stops it). The nanoCH32H417's VDDIO is the ME6211 LDO's 3.3 V shared with VDD33 (both cores), and the backlight's anode hangs on it with no series resistor, so the V5F's supply current swinging with a burst of floating-point work shows as brightness. The code side is to keep the fit's bursts short and regular (the cold start runs one seed a frame, `magFitSolveStep`); the fix is hardware - a resistor or a driver for the backlight from 5 V on the bench, and on V6 the backlight on its own driver and real bulk capacitance on the CH32's VDD33. Nothing that runs a burst of compute should be blamed on a supply until this is remembered.
